# 0002. 核心数据模型：决策记录

构建时不需要读这个文件；它记录为什么这样设计。构建规格见 [index.md](index.md)。

## Context

采集器的每个功能（实时消息流、历史补采、编辑删除留痕、附件、搜索、导出、关键词提醒，以及以后的 AI 分析和下单）都读写同一批数据。表结构一旦上线并积累了数据，再改主键、拆表或合表，就要做会破坏数据的迁移。所以 scope 把数据模型单独列为第 3 项，并要求它支撑后续切片而不需要这样的迁移。

几股力量塑造了这个问题：

- **同一条消息有多个入口。** 实时事件、历史补采、以后的多个账号，都可能写入同一条消息。scope 要求它只存一份。
- **消息会变。** KOL 发错交易消息后会编辑，或者删掉重发。你要看到最新内容，同时保留原文；以后的下单程序还要知道自己依据的内容是否已经过时，以便撤单。
- **Discord 本身的限制。** 补采只能拿到消息的最终版本；删除事件只带 ID 不带时间；链接的 embed 预览会在消息发出之后才补上，表现得像一次编辑。附件链接带签名，会过期。
- **规模和运维。** 单人自用，一台 80 GB 磁盘的服务器，预计每天几万条消息、永久保存。没有 DBA，表结构要简单到能直接用 SQL 查。
- **项目约定。** SQLAlchemy 2.x、Alembic、pyright strict、函数式风格、可预期的失败用返回值表达（`AGENTS.md`）；时间统一 `timestamptz`，NOTIFY 只带 ID（spec 0001）。

## Options considered

### Option 1：以 Discord ID 为主键的关系模型，消息表存最新版，版本表存旧版

服务器、频道、用户、消息直接用 Discord 的 snowflake ID（一个包含时间的 64 位整数）做主键；`message` 存当前内容和 `version`，每次编辑把旧内容追加到 `message_revision`；删除只打标记。

**Pros**:
- 去重靠主键冲突，零额外逻辑；按 ID 排序就是按时间排序。
- 常见查询（频道消息流、搜索、导出）只读一张表。
- 没编辑过的消息不占版本表空间。

**Cons**:
- 每次编辑要在一个事务里同时写两张表，写入函数比单纯的 INSERT 复杂。
- “当前内容”和“历史内容”分在两处，查完整历史要合并。

### Option 2：事件溯源（只追加的消息事件表）

只存一张 `message_event` 表（新建、编辑、删除各一行），当前状态由事件折叠出来，或者再维护一张由事件生成的视图。

**Pros**:
- 天然就是变更记录，下游程序按序号消费，审计最完整。
- 永远不改旧数据。

**Cons**:
- 每次显示消息都要折叠事件，或者额外维护一张派生表，两者都要处理一致性。
- 对单人工具来说，概念和代码量明显更重，查询也很难直接写 SQL。

### Option 3：原始 JSON 文档

每条消息存一个 `jsonb` 原始载荷，只拆出 ID、频道、时间几列用来建索引。

**Pros**:
- 不丢任何字段，以后想用什么都能从 JSON 里取。
- 模型几乎不用设计。

**Cons**:
- 每条多占 1 到 3 KB；查询和类型检查都绕不开 JSON 路径。
- 编辑和删除的语义仍然要单独设计，并没有省掉核心问题。
- 你已经明确选择不存原始数据。

## Rationale

选 Option 1，是因为它用最少的机制满足了三条硬需求。“同一条消息只存一份”交给主键；“看最新、留原文”交给 `message` 加 `message_revision` 两张表；“下游知道内容已过时”交给 `version` 和 `deleted_at`。这些都是普通的列和约束，不需要额外的派生表或折叠逻辑。

Option 2 最适合“按顺序消费变更”这个需求，但这个需求要等 AI 和下单功能才出现，而且只需要一张只追加的 `message_change` 表就能满足，不需要把整个模型改成事件溯源。所以这里只把它设计出来，等那时再建（你的选择）。Option 3 和你“不存原始 JSON”的选择冲突，也不解决编辑语义。

迁移分批建是按 Tracer Bullet 的做法：第 3 项只交付 Slice 1 链路要用的表，后面的表由后面的功能各自用只新增的迁移补上。因为整体模型已经在这里定好，后加的表只是新增，不会动已有的表。

### 我替你定下的细节

不太值得你逐个权衡的实现细节，每条写了理由和备选，不同意可以直接改：

- **状态和类别用 `TEXT` 加 `CHECK`**，不用 PostgreSQL `ENUM`。理由：状态值以后还会加（比如 `match_type` 加 `regex`），改 `CHECK` 比改 `ENUM` 简单，也不需要锁表。备选：`ENUM`（更省空间，但改动麻烦）。
- **自建实体用 `BIGINT GENERATED ALWAYS AS IDENTITY`，批次号用 `uuidv7()`**。理由：遵循 `postgresql-table-design` skill 的约定；批次号是 api 生成、用来分组的，不需要连续。备选：全部用 identity（批次号就要多一张表）。
- **外键默认 `RESTRICT`**。理由：服务器、频道、消息永远不应该被硬删除，数据库层面直接拒绝，比靠代码自觉更可靠。只有账号相关的关系（访问表 `CASCADE`、负责账号 `SET NULL`）允许跟着账号一起删，因为消息并不记录是哪个账号采到的。备选：全部 `CASCADE`（一个误删就会连带删掉所有消息）。
- **`reply_to_id` 不加外键**。理由：被回复的消息可能在采集范围之外，或者比采集开始的时间还早。备选：加外键并在缺失时置空（会丢掉回复关系）。
- **“无权限”不存在频道上，由 `account_channel_access` 算出**。这和访谈中展示的 `channel.status` 包含 `no_access` 不同：有多个账号时，一个频道能不能读取取决于每个账号，存在频道上会和访问表对不上。备选：保留 `no_access`，由 collector 同步维护。
- **`message.type` 只允许 0 和 19**（你的选择）。交叉检查指出，类型 20 和 23（机器人的斜杠命令和右键菜单命令回复）也是有内容的消息，有些信号机器人就是这样发的；你确认不采，代价写进了 index.md 的 Consequences。以后放宽只需要改 `CHECK`。
- **转发内容存进 `forwarded` jsonb**（你的选择）。Discord 的转发消息正文是空的，被转发的内容放在单独的快照里；不存的话，KOL 转发的信号就只剩一条空消息。它和 `embeds` 一样是拆好的结构，不是原始 JSON。
- **一个 `ingest_message` 处理插入和更新**。理由：实时事件和补采拿到的都是「这条消息现在的样子」，用同一个函数、同一张编辑判断表处理，就不会出现两条路径行为不一致；行锁加 `ON CONFLICT DO NOTHING` 处理并发。备选：插入和更新分成两个函数（调用方要自己决定调哪个，补采时容易漏掉编辑）。
- **内容不会倒退**。理由：补采和实时事件到达的顺序不确定；按 Discord 的 `edited_timestamp` 判断，比库里旧的快照直接丢掉。
- **补采对账只在任务 `done` 后进行**。理由：被限速或中途失败的任务没返回某条消息，不代表它被删了；误标删除会让下游错误撤单。
- **函数不提交事务**。理由：spec 0001 要求 INSERT 和 `NOTIFY` 在同一个事务里，事务边界只能由调用方掌握。
- **只是 embed 展开不算编辑**。理由：Discord 在链接预览生成后发送一次更新事件，但编辑时间不变；如果算作编辑，几乎每条带链接的消息都会多出一个假版本，下游程序还会误以为内容变了。判断依据是 Discord 的 `edited_timestamp` 是否改变；完整规则见 index.md 的编辑判断表。备选：每次更新都算一个版本（简单，但噪音很大）。
- **附件变化不加版本号**。理由：旧版本表只记文字和 embed；附件被拿掉用 `removed_at` 记录，信息不丢，又不会因为附件的变化让下游误以为文字改了。
- **删除时间用收到事件或发现的时间**。理由：Discord 的删除事件不带时间。补采发现的删除用 `delete_source = reconciled` 标明时间不精确。
- **实时覆盖用开放上界的 `tstzrange`，崩溃后在心跳时间关闭**。理由：上界就是「最后确定还在采集的时刻」；心跳只在 `online` 时写，所以以心跳为准是保守的，最多让补采多抓一小段。会话丢失时立刻关闭，RESUME 成功则不关，因为 RESUME 会补发断线期间的事件。备选：每次心跳都更新上界（写入更频繁）。
- **覆盖段允许重叠，计算缺口时用 `range_agg` 合并**。理由：写入时不用合并相邻的段，逻辑最简单；表很小。备选：用排除约束禁止重叠（需要 `btree_gist` 扩展和合并逻辑）。
- **`created_at` 存成列，而不是每次由 ID 算**。理由：按时间筛选和导出时可以直接用索引和比较；它由 ID 唯一确定，永远不会过期。备选：只存 ID，查询时计算。
- **`message_revision` 提前到第一次迁移**。理由：第 10 项补采（排在第 11 项前面）就需要写旧版本；一张空表几乎没有成本。
- **不分区**。理由：每天几万条，一年大约 1000 万行，普通 B 树索引就够；分区会让主键和外键都更复杂。阈值写在 index.md 的 Consequences 里。
