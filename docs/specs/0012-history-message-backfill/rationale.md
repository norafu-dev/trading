# 0012. 按时间段采集历史消息：决策记录

这里是 [index.md](index.md) 的理由部分，`/develop` 不需要读。

## Context

实时采集只能拿到开启开关之后的新消息。刚开始采集的频道没有以前的内容；小号断线、Mac 合盖、发布重启、开关关过再开，都会在覆盖记录里留下一段没采到的时间（缺口）。spec 0002 和 spec 0008 已经让覆盖记录（`channel_coverage`）和真实采集情况一致，所以缺口是可以准确算出来的；spec 0002 也已经为历史任务预留了表结构、状态流转和对账规则，并保证同一条消息不管从哪条路径进来都只存一份。

最大的约束是封号风险。selfbot 违反 Discord 服务条款，历史请求是这个产品里最集中、最像脚本的流量：一个大频道的全部历史可能是几十万条、几千页请求。节奏、限额和「出问题就停」必须是正式需求，而且要能在不重启的情况下调整。另一方面，只有 collector 进程持有登录会话（spec 0001、0005），任何 Discord 请求都只能从那里发出；api 和 collector 之间只通过 PostgreSQL 交流。

还有几个现实情况：只有一个使用者、一个小号；部署在一台 Lightsail 小机器上，CPU 是突发型；附件下载任务（spec 0011）已经在 collector 里作为后台循环运行，有自己的限速和暂停逻辑，补采进来的消息会自动排进它的队列；discord.py-self 收到 429 时大多自己等待重试，调用方看不到异常。

不做这个功能，数据就永远从开启那一刻开始，并且每次断线都会永久丢掉一段消息。

## Options considered

### Option 1：collector 里的历史任务循环，任务表按连续时间段拆行

在 collector 里加一个后台循环，和附件下载任务并列，用 `GatewayHandle` 里的当前会话发请求。建任务时就用 `tstzmultirange` 把请求的时间段减去已覆盖和已排队的部分，每段连续时间一行。一次只跑一行，从新到旧翻页，断点是一个消息 ID。节奏、限额和总开关放在单行设置表里。

**Pros**:
- 每行只有一个断点、一个进度、一段部分覆盖，逻辑最简单，重启、抢先、暂停都只是把状态改回 `pending`。
- 范围扣减在 SQL 里一次算完，和覆盖段用同一套运算。
- 和 spec 0011 的结构一致（循环挂在 `main.py`、会话句柄、单行设置表、心跳列），维护的人只需要理解一种模式。

**Cons**:
- 一次提交可能拆出很多行，界面要合并显示（后来按频道合并解决，见下面的「按频道合并显示」）。
- 拆分是在建任务那一刻算的；排队期间实时采集新覆盖的时间不会再被扣掉（最多重复发一些请求，数据不会重复）。

### Option 2：一个频道一行，跑的时候再跳过已覆盖的部分

任务行就是用户请求的原始时间段，collector 每翻一页前检查当前位置是否落在已覆盖的段里，落在里面就把断点直接跳到那一段的起点。

**Pros**:
- 库里行数少，和用户的操作一一对应，界面不用合并。
- 跳过判断用的是运行时最新的覆盖情况，排队期间新覆盖的部分也能跳过。

**Cons**:
- 进度、断点、部分覆盖都要处理「中间有洞」的情况：取消时要写多段覆盖，进度要扣掉跳过的时间。
- 跳过逻辑和翻页逻辑缠在一起，测试组合多，出错时可能漏掉一段而不自知。

### Option 3：在 Discord 客户端里同步一次性抓完

点「开始」后在 collector 里直接开一个协程，把这段时间翻完，不建任务表，进度存在内存里通过 NOTIFY 推给页面。

**Pros**:
- 代码最少，没有新表和状态机。

**Cons**:
- 重启、掉线就从头再来，大任务实际上跑不完。
- 不能排队、不能暂停、看不到历史，也没法做每日限额（重启后计数丢失）。
- 不满足 scope 第 10 项「中断后能从断点继续」。

## Rationale

选 Option 1，因为这个功能的风险集中在「长时间、可中断地发请求」，而 Option 1 让中断变得最便宜：任何意外都只是把一行改回 `pending`，断点是单调变小的一个数字，部分覆盖是一段连续区间。Option 2 的好处（运行时跳过新覆盖的部分）在这里价值很小：排队期间新增的覆盖只来自实时采集，它在请求时间段的末端，最多重复几页，而且 `ingest_message` 保证数据不重复；换来的却是断点、进度和部分覆盖都要处理多段的复杂度。Option 3 根本满足不了断点续传，也没法做跨重启的限额。

节奏选得保守，是因为封号是这个产品最不可逆的失败：默认每天最多 1500 页，一页 2 到 4 秒随机间隔，跑 20 分钟歇 5 分钟，大约是一个人快速往上翻聊天记录的速度，远低于 Discord 的限速线。滚动 24 小时而不是自然日，是为了避免在零点前后各跑满一次。429 的自动暂停数的是整个进程的限速，包括 discord.py-self 自己吞掉的那些，因为它们同样说明账号在被限制；只数异常的话，绝大多数 429 都看不到，这个保护就形同虚设。

删除对账从「任务 done 时整体对比」改成「整段重抓任务的每一个完整页」，是因为 Discord 返回的一页本身就是一段连续的消息 ID 区间，区间内没返回的就是不存在了，逐页判断是准确的；整体对比则要把一个任务见过的所有消息 ID 存下来（「全部历史」可能是上百万行），还会在任务中途取消时白白丢掉已经确认过的结果。这个改动只影响勾了「整段重抓」的任务，普通补采不做对账，和你的选择一致。

设置放在单行表、设置页可改，而不是环境变量，是因为这些数值很可能要在观察账号状态后反复调整，重启 collector 本身就会产生一次全新登录（spec 0005 和 0007 一直在避免它）。这也和 spec 0011 的附件存储设置保持同一种做法。

复核之后补上的几条保护都出于同一个原则：宁可停下等你看，也不要在不确定的时候继续发请求或改数据。没有「读取消息历史」权限时 Discord 返回空列表而不是报错，所以空的第一页不能当成「没有消息」，否则会写下假的覆盖段，整段重抓时还会把库里的消息误标成删除。401、Cloudflare 封禁和验证码说明账号本身可能有麻烦，直接关掉总开关，而不是让队列逐个任务去撞。休息和等限额时把任务放回队列，是为了让自动补缺口在这段时间里仍然能排到前面。缺口不设最短长度是有意的：重启留下的几秒缺口里也可能有真的消息，每个频道多花一页是可以接受的代价。

## 按频道合并显示（2026-11-05 修订 AC-14）

里程碑 3 做完以后，Option 1 唯一那条界面上的代价真的出现了：一个频道被实时覆盖切过几次，一次提交就能变成七八行，每行一个独立的进度条，一屏只看得下两三个频道，而你心里想的单位始终是「这个频道补到哪了」。所以 AC-14 改成按频道合并：一个频道在这个批次里有几段就合成一行，段落折叠起来，操作也从「段」提到「频道」。

合并放在前端做，而不是让接口返回已经合并好的频道行。接口继续按子任务返回行，加上按整个批次算好的合计。理由是服务端一旦有了「频道行」这个概念，断点、覆盖段、状态流转就得同时支持两种粒度，而这些恰恰是 Option 1 刻意保持简单的地方；页面上的合并只是读取时的一次变换，可以写成一个纯函数单独测，错了也只是显示错，不会写坏数据。代价是「已结束」分页时同一个频道的段可能跨页，合并只覆盖已加载的部分，这在一个单用户的回看列表里无所谓。

合并进度按每段的时间长度加权，而不是按段数平均，也不是按已抓条数。按段数平均时，collector 重启留下的几秒缺口和一段七天的任务一样重，一个几秒的小段没抓就能把进度压到 50%，完全是误导。按条数加权听起来更准，但在抓完之前没人知道总条数是多少，分母不存在。时间长度是建任务时就确定的分母，也正是单段进度自己用的那个分母，两级进度口径一致。

合并状态按「最需要你注意」取一个（失败 > 抓取中 > 已暂停 > 排队中 > 已取消 > 已完成），而不是显示一串数字，因为频道行是给人扫视的：你要的是「这个频道现在要不要我管」。要看细节就展开，有失败段时直接默认展开，不用你去找。各状态的段数仍然在批次标题里，那一行回答的是另一个问题，「这批还剩多少」。

频道级操作复用整批操作那段代码，只多一个 `channel_id` 过滤，所以状态表、加锁顺序和「只改状态符合的行」都是同一套，不会出现两种语义。批次里没有这个频道时沿用 404 `batch_not_found`，不新开一个错误码：频道行只从已经加载的数据来，分不清「批次不存在」和「频道不在批次里」对单用户没有任何实际差别，少一个错误码就少一处前后端要对齐的映射。重试暂时不做频道级，因为它和暂停三件事不同，失败原因可能逐段不一样（一段没权限、一段 `suspect_empty`），一键重试容易把你本来该看一眼的东西盖掉；真遇到一个频道整片失败再加（见 index.md 的 Follow-up）。

任务记录 30 天后删除是你的选择。它让 `history_job` 成为第一张会被定期删除的业务表，需要在 spec 0002 的不变量里加一个例外；覆盖段不删，所以删除任务记录不会让已经补过的时间重新变成缺口。
