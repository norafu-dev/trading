# 0003. Dashboard 界面基础：理由

## Context

dashboard 是你看采集结果的唯一窗口。scope 第 4 项要在 Slice 1 开始之前定下它的样子和基础组件，因为第 5 到 15 项的每个页面（登录、账号、频道管理、消息流、任务、搜索、导出、提醒）都会用到它。现在的前端只有一个显示 health 的脚手架页面，没有样式方案、没有 `DESIGN.md`、也没有任何组件。

几股力量在起作用。第一，这是只给你一个人用的工具，不需要 SEO、多语言和服务端渲染，前端是 Next.js 静态导出（spec 0001），所以任何依赖服务端或构建时就知道全部网址的做法都不行。第二，核心界面是消息流：一个频道可能有几万条消息，需要像 Discord 一样按人分组、渲染 Discord 自己的 markdown 方言（剧透、提及、自定义表情、时间戳标记），而且消息内容完全来自外部，必须当不受信任的数据处理。第三，你想要的视觉是 Discord 的结构加 Wise 的视觉语言，桌面为主，手机能看，两套主题跟随系统。第四，项目规则要求纯函数优先、`strict` TypeScript、只用具名导出、错误在一处转成界面状态，组件方案要能顺着这些规则写。

这一项本身是一个跨所有前端文件的规范，同时又在 scope 里有一个要构建、要验收的条目，所以 spec 里既有规范（`## Standard definition`），也有验收标准和构建步骤。

如果不先定下来，第 7 和第 8 项会在写业务的同时顺手发明样式和组件，几个页面很快就各长各的，之后统一的成本比现在一次定好高得多。消息列表的接口如果不先定，第 8 项的接口设计和界面会互相等待。

## Options considered

### Option 1: Tailwind CSS v4 加 shadcn/ui（Base UI），自定义 token

样式用 Tailwind v4，所有颜色、圆角、字体是 CSS 变量；基础组件用 shadcn/ui 的 CLI 复制进仓库，底层是 Base UI 提供的无样式、可访问的交互原件。消息列表、markdown 渲染这些 Discord 特有的部分自己写。

**Pros**:
- 组件代码在仓库里，按 Wise 风格改成药丸按钮、大圆角不受任何限制，每个组件是独立文件，需要哪个加哪个（你说的「模块化」）。
- token 就是 CSS 变量，跟随系统的深色模式只是一组 `@media` 里的覆盖值，不需要 JS。
- Base UI 处理焦点管理、键盘操作、弹出层定位这些容易写错的可访问性细节。
- 已经装了官方 `shadcn` skill，构建时按它的真实写法来。

**Cons**:
- 生成的组件成了自己的代码，shadcn 后续更新要手动对比合并。
- Tailwind 类名写在 JSX 里，长组件的可读性比单独的样式文件差。
- shadcn 的聊天组件不适合本项目，消息列表这块得完全自己写。

### Option 2: Mantine

一个开箱即用的完整组件库，自带主题系统、表单、表格、通知、深色模式。

**Pros**:
- 组件最全，频道管理和任务页需要的表格、表单直接能用，写得最快。
- 主题系统完整，深色模式和颜色变量都现成。

**Cons**:
- 组件是库里的代码，要改成 Wise 的药丸按钮和大圆角，得在它的主题 API 和样式覆盖上绕，越改越费劲。
- 包体更大，也多了一套自己的样式方案要学。
- 消息列表同样得自己写，省下的只是周边页面的工作量。

### Option 3: CSS Modules 加 Base UI，组件全部手写

不引入 Tailwind，每个组件一个 `.module.css`；交互原件用 Base UI，样式和组件全部自己写。

**Pros**:
- 对样式的控制最直接，样式和结构分开，读起来清楚。
- 依赖最少，没有生成代码要维护。

**Cons**:
- 按钮、提示、抽屉、骨架这些基础组件全部从零写，光这一项就多出好几天，而且一个人写的组件很难一次把可访问性做全。
- AI 辅助写 CSS Modules 的质量不如写 Tailwind 加 shadcn 稳定，后面每个页面都会慢一点。

## Rationale

选 Option 1，核心原因是「样子要自己定，交互细节不想自己写」。你要的 Wise 风格（药丸按钮、大圆角、亮绿配森林绿）和任何现成组件库的默认样子都差很远；Mantine 这种完整组件库在改样子时会一直和它的主题系统较劲，而 CSS Modules 全手写又要从零做焦点管理、键盘操作这些容易出错的东西。shadcn 正好在中间：组件代码在仓库里随便改，交互和可访问性由 Base UI 兜底。这也是你说的「模块化」：每个组件是一个独立文件，需要什么加什么。

主题和 token 选 CSS 变量加 `prefers-color-scheme`，是因为这个项目是静态导出，没有服务端能在首屏前知道你的主题偏好；跟随系统的纯 CSS 方案是唯一不需要 JS、也不会闪烁的做法。不做手动切换按钮也是这个原因，加按钮就要把选择存在浏览器里，并在首屏前用一段脚本读出来。

消息列表是这个项目的核心界面，也是唯一真正的性能热点，所以单独做了两个偏离 shadcn skill 的决定：用 TanStack Virtual 而不用 `MessageScroller`（后者不虚拟化），自己写 Discord 式的消息行而不用 AI 聊天气泡。代价是贴底和插入后保持位置这些滚动逻辑要自己写，所以 spec 把它们写成明确的验收标准，并要求在预览页用 5 万条假数据验证。markdown 选 Discord 官方的解析器，是因为 Discord 的方言（剧透、提及、表情、时间戳标记）和标准 markdown 差别很多，用官方实现能少掉一大类「Discord 里这样显示，我们这里不一样」的问题；它是 0.x 版本而且需要 WASM，所以构建计划的第二步就验证它在静态导出下能不能跑，不行就换备选。

最后，消息列表的组件接口在这一项先定死，而不是等第 8 项。这样第 8 项设计接口时有一个明确的目标（字符串 ID、提及名字、已编辑时间），界面也能先用假数据做完，两边不互相等待，符合 Tracer Bullet 每一段都能独立跑通的做法。
