# 0004. Dashboard 访问保护：理由

## Context

dashboard 部署在一台有公网域名的 Lightsail 服务器上。它能看到所有采集到的消息，第 6 项之后还能更新 Discord 账号的 token，以后可能还会放交易所密钥。任何拿到访问权的人，等于拿到了你的小号和全部数据。所以这一项虽然只有一个用户，安全标准要按「公网上的高价值目标」来定。

spec 0001 已经定下几条约束：认证在 FastAPI 一侧完成；前端是 Next.js 静态导出，由 Caddy 同源提供，线上没有 Node 进程，所以没有服务端能在页面渲染前拦截请求；用 cookie 会话；进程之间只通过 PostgreSQL 协作；api 只开一个 worker。项目规则还要求配置走 `pydantic-settings` 并在启动时校验、密钥不进 git、日志或前端、可预期的失败用返回值表达。

有几种力量在拉扯。一是安全和方便：你希望在常用设备上不必天天登录，但被偷的 cookie 不能永远有效。二是首次设置：部署上线和你完成设置之间有一段空档，网页上的设置入口可能被别人抢先使用。三是恢复：单用户系统没有「找管理员重置」这条路，验证器丢了必须有办法回来，而这条路本身不能变成后门。四是运维：这是一个人维护的项目，不想为了认证再多运行一个服务。

不先定下来的话，Slice 1 后面的每个接口都没有保护可挂，而第 6 项会把 Discord token 放进一个任何人都能访问的系统里。

## Options considered

### Option 1: 应用内实现「密码 + TOTP」，会话存数据库

在 FastAPI 里用 `argon2-cffi` 哈希密码、`pyotp` 校验 TOTP，会话表存在 PostgreSQL，cookie 只放随机值。首次设置靠服务器命令生成的一次性设置码，恢复靠服务器上的重置命令。

**Pros**:
- 不加任何新服务，完全符合「进程之间只通过 PostgreSQL」的架构。
- 二步验证让单独泄露的密码没用；会话可以随时作废。
- 任何设备上的浏览器都能登录，不需要装额外软件。

**Cons**:
- 认证流程是自己拼的，会话、限速、CSRF 防护都要自己测全。
- 没有现成的会话管理界面和恢复流程，要自己做（本项只做了最小的一部分）。

### Option 2: Passkey（WebAuthn）

用 `py_webauthn` 做无密码登录，设备上的指纹或 Face ID 就是凭据。

**Pros**:
- 防钓鱼能力最强，没有可以被偷的密码或可以被骗走的验证码。
- 登录体验最好。

**Cons**:
- 必须另做一套备用登录方式（设备丢了、换手机），最后往往还是回到密码。
- 注册和验证的流程、跨设备同步的行为都更复杂，测试也更难。
- 本地开发的 `localhost` 和线上域名是不同的 relying party，要分别处理。

### Option 3: 把 dashboard 放到 Tailscale 后面，不对公网开放

服务器加入你的 tailnet，Caddy 只在 tailnet 地址上监听，应用里不做登录。

**Pros**:
- 攻击面最小，公网上根本看不到 dashboard。
- 应用里几乎不用写认证代码。

**Cons**:
- 每台要用的设备都得装 Tailscale 并登录，临时用别的设备看不了。
- 要改部署：证书申请方式、Caddy 监听地址、防火墙都和 spec 0001 不同。
- 多依赖一个外部服务；Tailscale 账号本身成了新的单点。

### Option 4: 只用密码

和 Option 1 一样，但不加 TOTP。

**Pros**:
- 最简单，少一个依赖和一步操作。

**Cons**:
- 密码一旦泄露（重复使用、键盘记录、钓鱼），攻击者直接拿到 Discord token。对这个项目的风险来说不够。

### 子决定（逐个和你确认过）

| 决定 | 选择 | 备选 | 为什么 |
|---|---|---|---|
| 会话存储 | 数据库会话表 | 签名 cookie | 能立刻作废；单人使用时每个请求多一次查询可以忽略 |
| 过期 | 7 天不用，最长 30 天 | 24 小时、30 天不设上限 | 常用设备不用天天登录，被偷的 cookie 最多用 30 天 |
| 首次设置 | 网页设置，加一次性设置码 | 服务器命令写 `.env`、写库 | 你想在网页上完成；设置码堵住上线后的空档 |
| 设置码交付 | 服务器命令打印到终端 | 写进 api 日志 | 遵守「密钥不进日志」的项目规则 |
| 设置流程 | 设置码、密码、扫码、确认验证码 | 扫码就算完成 | 扫码失败也不会把自己锁在外面 |
| TOTP 密钥 | AES-256-GCM 加密存库 | 不加密 | 只泄露数据库备份时拿不到二步验证 |
| 加密格式 | AES-256-GCM，带版本号和用途名 | Fernet | 能换密钥，密文不能被挪用到别的用途；第 6 项沿用 |
| 恢复 | 服务器上的重置命令 | 备用码、两者都要 | 能 SSH 的人本来就控制一切，不多开一条路 |
| 防暴力破解 | 按 IP 逐步加长等待，加全局限速 | 锁定账号、交给 fail2ban | 攻击者没法把你永久锁在外面；状态在库里，本地和线上一致 |
| CSRF | `SameSite=Strict` 加 Origin 检查 | 再加 CSRF token | 同源部署下已经足够，前端不用管令牌 |
| 公开接口 | 登录相关接口和 `/api/livez` | 现有 `/api/health` 公开 | `health` 会暴露数据库状态；外部监控只需要知道进程活着 |
| 附加功能 | 只做登录记录 | 会话列表、改密码 | 你的选择；其余放进 Follow-up |
| 登录表单 | 一个表单 | 两步 | 不透露密码是否正确，也没有半登录状态 |
| 未登录体验 | 全屏加载后跳转 | 先显示空外壳 | 不让未登录的人看到 dashboard 的样子 |
| 中途过期 | 401 统一跳登录页 | 弹窗登录 | 一处处理，简单可靠 |
| 本地 cookie | `SESSION_COOKIE_SECURE` 开关 | 本地也上 HTTPS | 不改本地的 compose 和 Caddyfile |

## Rationale

选 Option 1，因为它是唯一同时满足「任何设备都能用」「不加新服务」「密码泄露也进不来」的选项。Tailscale（Option 3）的安全性最好，但它把成本转到了每一台设备和部署方式上，也和 spec 0001 已经定好的 Caddy 加公网域名的形态冲突；对一个偶尔要在别的设备上看一眼的私人工具来说，这个代价不划算。Passkey（Option 2）在体验和防钓鱼上更好，但单用户系统最难的恰恰是「设备没了怎么办」，它最终还是要一套密码之类的后备方案，等于做两套。只用密码（Option 4）对一个握着 Discord token、以后可能握着交易所密钥的系统来说太弱。

Option 1 最大的风险是「认证自己写」，所以这份 spec 把风险压在几个地方：最难写对的部分（密码哈希、TOTP 算法、加密）全部交给成熟的库；会话只是一个随机值的哈希，没有自己设计的令牌格式；受保护是默认值并由测试保证，忘记加认证的接口会让测试失败；限速和登录记录共用一张表，不引入第二份状态；所有判断逻辑都是注入时钟的纯函数，可以把 7 天、30 天、指数等待这些边界逐个测到。

首次设置和恢复都落在「能 SSH 上服务器」这一条信任边界上。这样网页上永远没有一个不需要秘密就能用的入口：设置需要服务器命令给出的设置码，恢复需要服务器上的重置命令。能 SSH 上服务器的人本来就能读 `.env` 和数据库，所以这两条路没有扩大攻击面。

把统一错误格式和加密格式放在这一项里定，是因为这一项第一个需要它们：登录要返回 401 和 429，TOTP 密钥要加密。把它们推迟到第 6 项会让这一项先发明一套临时格式，之后再改。
