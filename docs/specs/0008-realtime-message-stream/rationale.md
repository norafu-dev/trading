# 0008. 实时消息流：决策记录

## Context

第 8 项是 Slice 1 里真正让工具有用的一步。写入函数、覆盖段对齐、SSE 和消息列表组件都已经就位，缺的是 collector 接消息、消息接口和频道页。

影响设计的几股力量：

- **覆盖记录要可信**：第 10 项靠 `channel_coverage` 算缺口。覆盖段和实际存储的条件如果不一样，缺口就算错，而且很难发现。
- **事件的量不只来自已开启频道**：网关推送的是整个服务器的消息。每条都查库，开销都花在要丢掉的消息上。
- **错过的事件补不回来**：掉线或没存的编辑、删除，事后只能拿到最终版本。
- **用户账号的订阅是一个未决问题**：`discord.py-self` 2.1.0 的 `guild_subscriptions` 默认在启动时订阅全部服务器，文档说关掉后超过 75,000 人的服务器可能收不到消息事件，而且 `guild.threads` 只剩已加入的线程。spec 0005 把决定留给了这一项，spec 0006 AC-1 写的“不发订阅指令”和实际行为不符。
- **额度有限**：collector 重启要消耗每天 10 次的登录额度，所以一条坏消息不能让进程崩溃循环。
- **SSE 连接正常不代表通知都到了**：LISTEN 连接断开时浏览器不会重连，订阅者队列满了也会丢事件。

## Options considered

### Option 1: 内存名单加 SSE 只通知，只订阅有开启频道的服务器（选中）

存储条件是开放的覆盖段，用监督循环内存里的名单判断；SSE 只带 ID，前端统一按接口取数；服务器按需订阅。

**Pros**:
- 覆盖记录和数据一致，没勾选的消息零查询。
- 一条取数路径覆盖所有恢复场景。
- 流量最小，行为接近官方客户端。

**Cons**:
- 走库不推荐的订阅路径，线程不全，要多一个「加载线程」功能。
- 多一次取数请求，延迟略高。

### Option 2: 库默认全部订阅，其余相同

**Pros**:
- 不用改现有行为，不用「加载线程」，线程最全，是库推荐的用法。

**Cons**:
- 流量和内存最大，所有服务器的消息都要转换成快照再丢弃。
- 和官方客户端的行为差得更远。

### Option 3: 每条消息查库判断，SSE 带完整消息并按 Last-Event-ID 补发（spec 0001 原方案）

**Pros**:
- 监督循环没有新状态；浏览器少一次请求。

**Cons**:
- 没勾选的消息也要查库。
- 没打开的频道也要推全文；补发和分页是两套逻辑；LISTEN 断开而浏览器没重连时还是会漏。

### Option 4: collector 内存缓存 `collect_enabled` 名单

**Pros**:
- 不查库，打开开关后立刻开始存。

**Cons**:
- 开关的写入方是 api，要靠通知同步；存储条件和覆盖段不一样，覆盖记录会对不上。

## Rationale

存储条件选覆盖段，是因为第 10 项需要“标记为已采集”和“真的存了”是一回事。判断放内存是因为真正的开销在要丢弃的消息上，而覆盖段的写入方只有监督循环：它写完就能算出新名单，这份名单是事务结果的副本，不是一份要同步的配置，和 Option 4 不同。它放在不可变的 `SessionState` 里，也符合项目的 Functional 规则。

SSE 只通知，是把“实时”和“正确”分开：通知负责快，接口负责对。这样 Context 里说的两种静默丢通知也能靠轮询补上，不需要服务端再写一套补发。这改变了 spec 0001 的约定，你已确认。

订阅方式是你选的，和我的推荐（Option 2）不同。我推荐默认值，理由是代码最少、线程最全，也是库测试最多的路径。你选按需订阅，换来更小的流量和更接近官方客户端的行为；对一个封号是最大风险的工具，这是合理的取舍。代价是「加载线程」这个功能和几项要实测的未知行为，都写在 Consequences 和 Follow-up 里。构建计划先用默认订阅打通链路，最后才切换，所以切换出问题时，把一个参数改回去就能恢复接收。

退订留到下一个会话，是因为来回开关不该变成来回发网关指令，多出来的消息已经由名单丢弃。

写入失败分两类，因为两种风险相反：数据库真的断了时，继续跑会让覆盖段虚报，所以重试后退出；单条坏数据时，退出只会崩溃循环耗尽登录额度，所以跳过。

`thread_load_requested_at` 在发出订阅后就清空，比确认数据模型时说的“下次全新登录后清空”更早。写设计时发现，api 无从知道 collector 内存里的订阅状态，这一列只能表示“请求还没被处理”，页面靠它显示“正在加载”。订阅本身仍然保持到这个会话结束，所以你看到的行为不变。

我替你定下的细节（不同意可以直接改）：

- **事件用 `raw_message_edit` 和 `raw_message_delete`**：消息不在库的内存缓存里也会触发。备选 `message_edit`，重启后的旧消息会漏。
- **回复消息总是另起一组**：这样引用行有地方放，和 Discord 一致。备选：同组内也显示引用，行高和分组都会变复杂。
- **摘要 100 个字符、纯文字，后端算好**：备选前端截断，那样接口要返回被回复消息的全文。
- **`after` 积压时重载最新页**：不连续翻很多页追赶。备选循环追赶，会一次拉很多数据，而这些旧消息用户往上滚动时也能取到。
- **30 秒轮询取最新页，不用 TanStack 的 `refetchInterval`**：它会重取所有已加载的页。备选只用 `after`，就发现不了最新页里的编辑。
- **事件总线不走 React 状态**：避免每条消息重新渲染整个外壳。备选放进 context，代码少一点，但繁忙时会卡。
- **未读圆点也放到服务器图标栏**：侧栏只显示当前服务器，不放的话其他服务器的未读看不到。
- **重试放在监督循环内并阻塞它**：这样事件顺序不变。备选后台重试，会让同一条消息的新增和编辑乱序。
- **不加单独的消息写入批处理**：还没有测到性能问题。
