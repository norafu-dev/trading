# 0013. 消息搜索与筛选：决策记录

这里是 [index.md](index.md) 的理由部分，`/develop` 不需要读。

## Context

采集器已经能把实时和历史消息存进 `message` 表，但 dashboard 只能一个频道一个频道往上翻。scope 第 13 项要求按关键词、频道、作者、时间范围找消息，「在大量消息里也很快返回」，并且能跳到上下文。导出（第 14 项）要按「当前筛选结果」导出，它的设计已经停下来等这里把筛选的形状定好。(basis: scope 第 13、14 项；导出设计暂停时的记录)

数据的特点决定了搜索的难点。你采集的消息中英混合，常搜的是两三个字的短词（「空投」「ETH」）和币名、缩写这类词典里没有的新词。你要的命中规则是不分大小写的子串包含，和第 15 项关键词提醒一致。预计一年后几百万条消息。PostgreSQL 自带的全文检索按词切分，对中文没有可用的分词；而子串搜索要快，就需要一种能处理两个字的索引。(basis: spec 0001 技术栈表「搜索默认先用 PostgreSQL 自带能力，中文分词在第 13 项单独决定」)

运维上的约束：数据库用的是 `pgvector/pgvector:pg18` 官方镜像，CI 的集成测试连同一个镜像的真实 PostgreSQL，备份和恢复（spec 0009）也围绕它。任何需要编译或额外安装的扩展，都要自建数据库镜像，并让 CI、生产、恢复演练都换过去。表结构只能通过 Alembic 迁移修改，并且只新增、不改已有的列。(basis: AGENTS.md 的规则；spec 0002 的迁移约定)

现在的频道页只能取最新一页、更早、更新和指定 ID 的消息，没有「以某条为中心」的加载方式，也没有定位和高亮某条消息的能力，所以「跳到上下文」需要在频道页上补一种模式。

## Options considered

### Option 1：内置的二元切片数组索引

在 `message` 上存一列小写的搜索文字，用一个 `IMMUTABLE` SQL 函数把它切成相邻两个字的去重数组，建 GIN 表达式索引。查询时每个词也切成二元切片，用数组包含（`@>`）走索引找出候选行，再用 `LIKE '%词%'` 精确复核。原理和 pg_bigm 一样（二元组倒排索引加复核），只是用 PostgreSQL 内置的数组 GIN 实现。(basis: 倒排索引加复核是子串搜索的通用做法)

**Pros**:
- 两个字的词也能走索引，不依赖分词词典，新词和缩写不会漏。
- 不装扩展，不改镜像，CI 和生产完全一样，备份恢复流程不变。
- 行为完全由项目代码决定，能在集成测试里用 `EXPLAIN` 断言。

**Cons**:
- 索引大，大约每个字一个条目；几百万条时可能有几个 GB。
- 很常见的两字组合命中范围很大时，索引帮不上多少忙。
- 搜索文字是存下来的派生数据，规则改了要整体重建；要自己写补建任务。
- 没有相关度排序和分词，以后要这些得换方案。

### Option 2：pg_trgm（三元组索引）

PostgreSQL 自带的 contrib 扩展，`pgvector` 镜像里就有，`gin_trgm_ops` 索引直接支持 `ILIKE '%词%'`。

**Pros**:
- 最省事：一个 `CREATE EXTENSION` 加一个索引，不用存额外的列，`ILIKE` 直接不分大小写。
- 成熟，文档完整。

**Cons**:
- 官方文档写明，提取不出三元组的模式会退化成扫描整个索引；两个字的词正好提取不出三元组，而这是你最常搜的。(basis: PostgreSQL 18 的 pg_trgm 文档)
- 中文字符是否被当成单词字符取决于数据库的区域设置，需要实测，存在不确定性。

### Option 3：pg_bigm，自建数据库镜像

专门为中日韩文字设计的二元组全文索引扩展，一两个字的 `LIKE` 查询都能走索引。

**Pros**:
- 为这个场景而生，索引格式比通用数组 GIN 更紧凑。
- 查询直接写 `LIKE`，不用自己维护切片函数。

**Cons**:
- 需要在 `pgvector` 镜像上编译安装，并加进 `shared_preload_libraries`；CI、生产、恢复演练都要换成自建镜像，发布流程多一个镜像要维护。
- 只支持 `LIKE`，不支持 `ILIKE`，不分大小写仍然要存一列小写文字，省下的工作有限。
- PG18 的支持只在二手来源（发行信息镜像、云厂商发行说明）里看到，官方文档只覆盖到较早的版本，没有核实。

### Option 4：PGroonga，自建数据库镜像

基于 Groonga 全文引擎的扩展，支持中文、自带查询语法、相关度和高亮。

**Pros**:
- 功能最强：分词、ngram、相关度、高亮、查询语法都有。
- 有 PG18 的官方软件包（4.0.4 起），最新 4.1.0（2026-10-09）。

**Cons**:
- 依赖最重：要加 Groonga 的软件源，官方 Debian 安装页只列了 trixie；没找到 PG18 的官方 Docker 镜像，也没有和 pgvector 合并的镜像，只能自建。
- 一个外部全文引擎跑在数据库里，出问题时排查成本高，对一个单人工具来说过度。

## Rationale

决定性的力量是「两个字的中文词要快」加上「运维要简单」。pg_trgm 在第一条上直接不及格：官方文档确认两个字的模式会退化成整个索引扫描，而这正是你最常见的搜索。剩下的三个方案都能处理两个字，区别在于代价放在哪里。pg_bigm 和 PGroonga 把代价放在运维上：自建并维护一个数据库镜像，让 CI、生产、备份恢复都换过去，而且 pg_bigm 的 PG18 支持没能核实，PGroonga 没有现成的 PG18 加 pgvector 镜像。对一个你一个人维护、跑在一台 Lightsail 上的工具，这是长期的负担，而且出事的地方恰好是最不想出事的数据库。(basis: boring technology；减少需要运维的组件)

Option 1 把代价放在磁盘和一点代码上：索引更大，要多写一个切片函数、一个搜索文字生成函数和一个补建循环。这些都是项目里的普通代码，能单元测试、能在 CI 的真实 PostgreSQL 上用 `EXPLAIN` 证明走了索引。几百万条消息的规模下，索引大小可以接受，而且 pg_bigm 本质上做的也是同样的二元组倒排加复核，所以性能是同一个量级。因为 pg_bigm 不支持 `ILIKE`，选它也一样要存小写文字列，Option 1 多出来的只有切片函数。(basis: pg_bigm 文档的「仅 LIKE」说明)

几个连带的选择：

- **搜索文字由写入代码算好存成列，而不是数据库生成列**。附件文件名在另一张表，生成列拿不到；规则（Discord 标记处理、embed 字段选择）写在 Python 纯函数里更好测。备选：生成列加附件名单独索引，查询里每个词要多一次 `OR`，规则也要写在 SQL 里。
- **补建放在 api 的后台任务里，而不是一次性命令或迁移**。不用记得手动跑，发布和恢复备份之后都会自己补；补完后每 10 分钟复查一次，兜住发布期间旧版 collector 写入的行。备选：一次性命令（要写进手册、容易忘）；迁移里补（数据多时发布会卡住）。
- **每个词至少两个字**（你在设计过程中定的）。这样索引只存二元组、不存单字，体积小一些，而且每个词都有非空的切片，查询总能用上索引。
- **结果最新在前、按 ID 游标翻页，不按相关度**。聊天短消息的相关度意义不大，ID 倒序能直接走主键，和频道页、导出的顺序一致。备选：相关度排序（需要打分，翻页慢）。
- **总数封顶 1000、单独请求**。常见词数精确总数可能很慢，封顶后不影响第一页。备选：精确总数。
- **结果是快照，不实时更新**。搜索是翻旧账，滚动时结果不跳；实时看新消息用频道页。备选：命中新消息时提示，和第 15 项关键词提醒重叠。
- **跳到上下文用频道页的「以某条为中心」模式**，而不是在搜索页里展开前后几条。上下文可以无限滚动，以后回复跳转、关键词提醒都能复用。备选：搜索页内预览（只能看固定几条）。
- **筛选格式前后端各一个解析函数，共用用例文件**。网址、搜索接口、以后的导出接口用同一组参数；共用用例保证两边规则不分叉。备选：等导出时再定（可能写两套）。
- **固定查询计划，不靠计划器估算**。两轮交叉检查都指出：二元切片的统计只记录最常见的 1000 个元素，几个切片又高度相关，计划器可能把罕见词估成常见词（按主键倒序逐行过滤，扫完整张表），或者反过来。所以含包含词的查询在事务里关掉索引扫描和全表扫描，只剩「GIN 结果和其他索引取交集」的位图计划；`force_custom_plan` 让 asyncpg 的预备语句也按实际参数规划。代价是不加筛选的常见词要取回全部命中再排序，由超时兜底。备选：`force_custom_plan` 加 `ANALYZE`，交给计划器（不稳定，测试也会时好时坏）；`MATERIALIZED` CTE 强制先走 GIN（效果相近，但不能和其他筛选的索引取交集）。
- **超时 10 秒（搜索）和 5 秒（总数）**。你没有定硬性的速度指标（「用着不卡就行」），超时是为了让极端的宽泛查询不拖住数据库连接，并给出「加筛选」的提示。备选：不设超时。
