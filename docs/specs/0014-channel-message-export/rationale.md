# 0014. 频道消息导出：决策记录

## Context

采集器已经把消息、编辑前的旧版本、删除标记和附件都存进了 PostgreSQL 和 R2，但这些数据只能在 dashboard 里一条条看。你需要把某个频道里的一段对话拿出来：留档、放进表格里看，或者交给别的程序和 AI 处理。这段对话的边界通常是“从这条消息到那条消息”，而不是一个整齐的时间段。

几个约束决定了这个问题的形状。api 是单个 worker，跑在一台小的 Lightsail 机器上，一次导出不能把内存撑满，也不能长时间卡住别的请求。导出的内容必须内部一致：边导出边有新消息、编辑和删除进来时，文件里不能出现同一条消息的两个状态或漏行。进程之间只通过 PostgreSQL 交流，不能引入新的队列或存储。文件要能被 Excel 这样的软件直接打开，也要能被程序可靠解析，而 Discord 的 ID 是 18 位以上的整数，超过 JavaScript 和 Excel 能精确表示的范围。

另外，原来 scope 第 14 项写的是“导出当前筛选结果”。你在这次设计里把它收窄成“一个频道里的一段消息”，所以这里不讨论搜索结果的导出。正文里的 Discord 提及标记对你没有用处，导出时应当去掉。

如果不做这个功能，数据只能留在 dashboard 里，离开它就无法使用，也没有办法把一段完整的对话交给其他工具。

## Options considered

### Option 1: 浏览器直接下载，api 在只读快照里按批流式输出

前端在频道页里定下两端，先调预览接口拿条数和缺口，再让浏览器打开下载链接。api 在一个 `REPEATABLE READ READ ONLY` 事务里，用 `(channel_id, id)` 的键集分页（每次从上一批最后一条往后取，而不是用偏移量）每批取 500 条，转成文本行直接发出去。

**Pros**:
- 不加表、不加进程，完全沿用现有架构；快照保证文件一致。
- 内存只和批大小有关，和总条数无关。
- 浏览器自己管理下载进度、暂停和保存位置。

**Cons**:
- 写文件中途出错只能断开连接，文件被截断，没有办法在文件里说明。
- 下载期间一直占着一个数据库连接和快照。

### Option 2: 任务表加后台生成文件

点下载时在任务表里建一行，后台用 `FOR UPDATE SKIP LOCKED` 领任务，把文件生成到 R2，完成后前端拿签名链接下载，可以保留导出历史。

**Pros**:
- 生成过程和下载分开，失败可以重试，文件可以多次下载。
- 能显示进度和导出历史。

**Cons**:
- 要加迁移、后台循环、R2 上的临时文件和清理规则，代码量多好几倍。
- 你已经决定不记录导出历史，10 万条上限内流式下载足够快，这些能力用不上。

### Option 3: 前端分页拉取，在浏览器里拼文件

前端复用现有的消息分页接口一页页拉，在浏览器里拼成 CSV 或 JSONL，再用 Blob 触发下载。

**Pros**:
- 后端几乎不用改。
- 前端能精确显示进度。

**Cons**:
- 没有快照，分页过程中的编辑和删除会让文件前后不一致。
- 10 万条消息和它们的旧版本全部放在浏览器内存里；旧版本、附件的媒体状态现有接口也不全给，要改接口。
- 文件生成逻辑在 TypeScript 里，和后端的标记处理规则要写两份。

## Rationale

选 Option 1，因为它正好满足 Context 里最硬的两个约束：文件必须内部一致，服务器内存不能随条数增长。一个只读的 `REPEATABLE READ` 事务给出整次导出共用的快照，键集分页每次只取 500 条，而且走现有的 `(channel_id, id DESC)` 索引，不需要服务端游标（asyncpg 的游标打开期间不方便在同一个连接上再查附件和旧版本）。这和上次已经定下的“api 流式下载，不建任务表”一致。

Option 2 的能力（重试、历史、进度）在你“不记录导出历史”“一次最多 10 万条”的前提下用不上，却要多一套任务表和 R2 临时文件，违背“简单优先”。Option 3 最省后端，但没有快照，而且把标记处理规则复制到前端，和 spec 0013 已经建立的“后端一处纯函数”做法冲突。

流式下载的代价是中途出错只能截断。我们把能提前发现的错误（参数、范围、上限、空频道）全部放在第一个字节之前检查，并且先走预览接口，所以真正在中途失败的只剩数据库故障和超时，这对一个人用的工具是可以接受的。

### 小决定

- **范围用消息 ID 而不是时间**：你选择“从某条消息到某条消息”。ID 是 Discord 的雪花 ID（按时间递增），范围查询和排序都直接走索引，两端包含得很精确。
- **选择在导出模式里点两条**：不给每条消息加按钮，避免平时界面变乱；点的先后无关，减少出错。
- **开放的一端**：用「从最早」「到最新」代替“先滚到头再点”。
- **线程不展开**：导出的是一段连续的对话；线程本身也是频道，可以单独导出。
- **正文标记**：复用 spec 0013 的规则，拆出不改大小写和空白的 `strip_markup`，搜索和导出共用一处。备选是只去掉用户和身份组提及、把频道和时间戳换成可读文字，但多一套转换，而你认为提及没有用。
- **时间按浏览器时区写偏移**：读起来就是本地时间，同时带偏移不会有歧义。备选是一律 UTC，更标准但读的时候要换算。
- **CSV 加 BOM、RFC 4180**：Excel 直接打开中文不乱码，其他工具也都认。
- **ID 写成字符串（JSONL）和普通数字（CSV）**：JSONL 里用字符串避免 JavaScript 丢精度；CSV 里不加 `="..."` 这种只对 Excel 有用的技巧，保证 Python 等工具读出来是干净的值，代价写在 Consequences 里。
- **附件给 dashboard 链接**：`/api/media/{id}` 不会过期且需要登录；Discord 原链接几天就失效，打包 ZIP 太重。
- **每批 500 条**：每批再查附件、媒体和旧版本三次，500 条时每次查询都很小，单批内存也小；备选 1000 条，查询次数更少但单批内存翻倍。
- **上限 10 万条**：你选择的，保护小机器；预览和下载两处都查。计数用 `LIMIT 100001` 封顶，大频道两端都开放时不用扫完整个频道，代价是超过上限时只能显示「超过 10 万条」，看不到精确条数。
- **CSV 防公式注入**：正文是别人在 Discord 里写的，以 `= + - @` 开头的单元格在 Excel 里会当成公式执行，可能把数据外传。CSV 的主要用途就是 Excel 打开，所以给这类文字单元格加 `'` 前缀；备选是不处理、只在文档里提醒，但风险落在最常用的那条路上。
- **会话由路由管，而不是生成器**：浏览器在第一个字节之前就断开时，生成器根本不会运行，交给它管就会漏掉连接；所以用 `AsyncExitStack` 加 `BackgroundTask` 兜底。
- **超时 30 秒、空闲 5 分钟**：单条批量查询远低于 30 秒；下载卡住时 5 分钟后放掉快照，避免长时间阻碍 PostgreSQL 的清理。
- **不限制同时导出的个数**：只有你一个人用，每个导出只占一个连接；加限制需要进程内共享状态，项目规则不鼓励。
- **缺口提示复用 `channel_gaps`**：现成的缺口计算，只需要一个纯函数和范围取交集。
