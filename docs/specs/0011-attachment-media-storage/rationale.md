# 0011. 附件与图片保存：决策记录

## Context

Discord 的附件链接带过期签名（链接里的 `ex` 参数），大约一天后就打不开。现在 `attachment` 表只存了元数据和当时拿到的链接，dashboard 显示附件时只有文件名和大小。消息被删除或附件被编辑拿掉之后，这个工具本来要做到的「留痕」就缺了最有价值的一块：当时发出来的图和文件。

要保存的不只是消息自带的附件。转发消息里的附件（现在 `forwarded.attachment_names` 只存文件名），以及 embed 里机器人用 `attachment://` 上传、最终指向 `cdn.discordapp.com/attachments/...` 的图片，同样会过期。第三方网站托管的 embed 图不会因为 Discord 的签名过期，但下载它们意味着服务器要按别人消息里写的地址发请求，可能被引向内网或云平台的元数据地址。

几个现实约束：服务器是 2 GB 内存、约 60 GB 磁盘的 Lightsail，同时跑 PostgreSQL、api、collector 和 Caddy；api 只开一个 worker；进程之间只能通过 PostgreSQL 交流；collector 每次重启都会消耗一次 Discord 登录额度，所以设置不能靠重启生效；用户已经有 Cloudflare R2 账号，每日备份在用它；数据库备份是 `pg_dump`，文件不在里面。上线时库里已经有一批附件，它们的链接大多已过期，要拿回来只能用小号会话向 Discord 换新链接，这是带登录信息的请求，和封号风险相关。

不做这件事，每过一天就有一批附件永久丢失，越晚做丢得越多。

## Options considered

### Option 1：服务器本地磁盘加 collector 下载，api 直接发文件

collector 把文件下载到挂进容器的 Docker 卷，api 用 `FileResponse` 同源返回。

**Pros**：
- 零外部依赖，代码最少，本地开发和线上一样。
- 读文件没有额外的网络往返。

**Cons**：
- 附件和数据库抢同一块 60 GB 磁盘，满了会拖垮 PostgreSQL。
- 文件不在 `pg_dump` 里，还要另外做文件备份到 R2，等于把 R2 的活再干一遍。
- 所有文件流量压在单 worker 的 api 和 2 GB 服务器的带宽上。
- 同源返回用户上传的 HTML、SVG，要单独防止被当成网页执行。
- 换服务器时要搬文件。

### Option 2：私有 R2 桶加 collector 内的下载队列，api 跳转到签名链接（选定）

collector 在入库事务里建 `media` 行，主进程里的下载任务按队列下载、去重、生成缩略图、上传 R2；api 验登录后 302 到 1 小时的签名链接。

**Pros**：
- 不占服务器磁盘和带宽；R2 自带冗余，不需要另做附件备份；下载流量免费。
- 换链接直接用 collector 已登录的会话，不需要第二个拿 token 的客户端。
- 文件在 R2 的域名上打开，和 dashboard 不同源，天然隔离恶意附件。
- 和已有的 R2 账号、`NOTIFY` 加轮询、任务表的做法一致。

**Cons**：
- 多一个外部依赖和两组密钥要管。
- 下载代码跑在 collector 进程里，写得不好会影响采集（用独立任务和异常隔离来降低）。
- 签名链接每次不同，浏览器缓存要靠给 302 响应本身加缓存头。

### Option 3：独立的 fetcher 进程加 R2

和 Option 2 一样存 R2，但下载放在一个新容器里。

**Pros**：
- 下载出问题、内存涨高都不影响 collector。
- 可以单独发布，不消耗登录额度。

**Cons**：
- 换链接要用同一个 token 再开一个 Discord 客户端，同一账号两处登录，更容易被识别为自动化。
- 多一个容器、一套配置和一份心跳，2 GB 服务器上又多一个常驻进程。

### Option 4：api 从 R2 读出再转发给浏览器（代理）

存储同 Option 2，但浏览器始终只访问自己的域名，api 负责读 R2 并流式返回。

**Pros**：
- 链接永远在自己域名下，没有签名链接泄露的问题。
- 可以在 api 里做细粒度控制（例如按次计数）。

**Cons**：
- 所有附件流量经过单 worker 的 api 和服务器带宽，看视频时会拖慢 dashboard 的其他请求。
- 同源返回用户文件，要额外防 XSS。
- 失去 R2 免费下载流量直达浏览器的好处。

## Rationale

最重的约束是服务器本身：2 GB 内存、一块磁盘同时承载数据库，api 只有一个 worker。附件是唯一会无限增长的数据，放进本地磁盘（Option 1）等于把「磁盘满了数据库挂掉」这个故障提前埋好，还要再为文件单独做一套备份。R2 正好解决两件事：容量和本地磁盘无关，持久性由 Cloudflare 负责，spec 0009 留下的「附件怎么备份」也就不需要再回答。用户已经在用 R2，没有新增供应商。

下载放在 collector 而不是新进程（Option 3），是因为过期链接只能用已登录的小号会话去换。再开一个客户端就是同一个账号两处登录，这正是这个项目最怕的封号信号。代价是 collector 多了一个任务，所以把它做成和 Discord 会话无关的独立 asyncio 任务，网络操作都在事务外，失败只影响那一行，不影响收消息。补下载期间带登录信息的请求会增加，所以换链接单独限速（50 个一批，至少隔 30 秒），账号不在线时不发。

读文件用签名链接跳转而不是代理（Option 4），同样是为了不让文件流量压在单 worker 的 api 上；跳转还顺带把文件放到和 dashboard 不同的域名上，恶意的 HTML 或 SVG 附件碰不到会话 cookie。1 小时有效期加 50 分钟的跳转缓存，是在「滚动回去不重复请求、视频播放中途不失效」和「链接泄露的窗口」之间取的平衡。

几个由我定下的细节：
- **统一的 `media` 表**，而不是给 `attachment` 加列（spec 0002 的预留）：转发附件和 embed 图没有 `attachment` 行，三套状态会让下载队列拼三处。次选是 `attachment` 加列再为另两类各建表。
- **按「频道 ID / 年月 / 哈希」存（`stored_file`）**：这是你定的。R2 控制台里能按频道和月份浏览，以后清理也能按前缀整组处理。同一频道同一个月内仍按内容去重，文件名由内容决定，所以上传天然幂等，崩溃重试不会产生脏数据。代价是跨频道或跨月的相同文件各存一份；删除时仍要数引用，而这个功能本来就不删。我原本推荐的是全局按哈希存（去重最彻底），再次一些的是按附件 ID 各存一份。
- **`claimed_at` 列**：collector 有单实例锁，所以启动时可以直接把上次没处理完的行放回去，不需要租约超时；可重试的失败才计入 `attempts`，崩溃不消耗重试次数。次选是用 `next_attempt_at` 当租约，崩溃后要等租约过期。
- **只下载 Discord 托管的 embed 图**：第三方图片不会因为签名过期，而按任意地址下载会把服务器变成别人能指挥的请求发起方。主机名白名单加禁止重定向，比自己挡内网 IP 和 DNS 换地址简单可靠得多。
- **队列按 `message_id` 从大到小**：新消息的链接还新鲜，先下不用换链接；补下载从最近往回补，你最可能看的先好。次选是按入库顺序，开始补下载时新附件会排在整个库存后面。
- **缩略图长边 800 像素 WebP**：消息流里一屏可能十几张截图，原图会让滚动卡、手机费流量。视频不做封面，因为那需要 ffmpeg，在 2 GB 服务器上不值得。
- **签名链接用响应头覆盖设置类型和文件名**：同一个文件可能被不同的消息以不同名字发出，上传时写死元数据做不到按行给文件名。是否生效列为 `/check verify` 的确认项。
- **`MEDIA_STORAGE` 必填、没有默认值**：线上忘了配置时，如果默认 `local` 会把文件悄悄写进容器的临时层，重启就没了；必填让它直接启动失败，符合项目「缺配置就报错退出」的规则。
